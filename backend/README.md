# Carte Pro API

Built with [Bun](https://bun.sh/) and [Elysia](https://elysiajs.com/).
Data lives in PostgreSQL, accessed through [Drizzle ORM](https://orm.drizzle.team/).

## Setup

Install dependencies:

```bash
bun install
```

Copy the environment file and fill in real values:

```bash
cp .env.example .env
```

Start PostgreSQL:

```bash
docker compose up -d
```

The database is initialised from `db/init.sql` the first time the container
starts. If you change that file later, it will not apply automatically since
Docker only runs it on an empty volume. Reset with `docker compose down -v`
if you need the new schema applied.

Start the API:

```bash
bun run dev
```

The server watches for file changes and reloads automatically. It listens on
`https://localhost:3000` using the certificates generated by
`../generate-certs.sh` (see the root README).

## Environment variables

| Variable | Purpose |
| --- | --- |
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | PostgreSQL connection |
| `PORT` | Port the API listens on |
| `FRONTEND_URL` | Allowed origin for CORS, must match the frontend's real URL |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | Sign session tokens |
| `QR_JWT_SECRET` | Sign the short-lived tokens embedded in payment QR codes |

## Routes

Interactive docs (Swagger UI, OpenAPI 3.0): `https://localhost:3000/openapi`
while the server is running. Not under `/api`, it sits at the server root.

All routes are prefixed with `/api/v1`. Request and response shapes are
defined next to each route with TypeBox.

`/auth`

- `POST /login`: log in as an employee, partner or admin
- `POST /logout`: clear the session cookie
- `GET /me`: get the currently authenticated user

`/employees`

- `POST /register`: register a new employee
- `GET /balance`: real-time balance
- `GET /transactions`: transaction history for the logged-in employee
- `POST /qrcode`: generate a single-use payment QR code

`/partners`

- `POST /register`: register a new partner
- `GET /search`: search validated partners by name or address
- `GET /transactions`: transactions for the current partner
- `POST /transactions`: redeem a QR code to charge an employee

`/admin`

- `GET /accounts`: list all employee and partner accounts
- `GET /scoreboard`: national dashboard aggregates
- `POST /partners/:id/validate`: validate or reject a partner
- `POST /credit-grants`: grant credit to an employee
- `GET /transactions.csv`: export the full transaction history as CSV

## Adding a route

Each resource has its own file in `src/routes/` (`auth.route.ts`,
`employee.routes.ts`, `partners.routes.ts`, `admin.routes.ts`). A route file
is a standalone `Elysia` instance with a `prefix`, registered in
`src/index.ts` with `.use(...)`.

To add an endpoint to an existing resource, add a handler to its file:

```ts
.get("/example", async ({ authUser, set }) => {
    // authUser is only defined behind requireEmployee / requirePartner / requireAdmin
    return { hello: "world" };
  },
  {
    beforeHandle: requireEmployee, // omit for a public route
    response: { 200: t.Object({ hello: t.String() }) },
    detail: { summary: "Short description", tags: ["employee"] },
  }
)
```

To add a whole new resource, copy the shape of an existing route file,
give it its own `prefix`, export it, then import and `.use()` it in
`src/index.ts` next to the others.

Always declare a `response` schema. Elysia validates the body against it
and it is what shows up in `/openapi`.

## Scripts

```bash
bun run seed        # fill the database with sample data
bun run add_admin    # create an admin account, prints the generated email and password
```

There is no public sign-up for admin accounts. Use `add_admin` to create the
first one.

## Database schema

The Drizzle schema in `db/drizzle/schema.ts` is generated from the live
database with `bunx drizzle-kit pull`. After regenerating it, replace any
`unknown("email")` with a proper `citext` type:

```ts
import { customType } from "drizzle-orm/pg-core";

const citext = customType<{ data: string; driverData: string }>({
  dataType() {
    return "citext";
  },
});
```

`db/init.sql` is the source of truth for the actual table definitions, keep
it in sync by hand when the schema changes. For the entity relationship
diagram and the full index list, see `../documentation/database.md`.

## Concurrency and balance protection

Two payments hitting the same employee's balance at the same time are
handled at the database level, not in application code.

The `check_sufficient_balance()` function runs as a `BEFORE INSERT` trigger
on `transactions` (see `db/init.sql`). It calls
`pg_advisory_xact_lock(NEW.employee_id)`, which locks that employee's id for
the rest of the current transaction.

If two charges arrive together: the first one to reach the lock reads the
balance, checks it is enough, inserts the debit, then releases the lock on
commit. The second one was waiting on that same lock, so it only resumes
once the first is done. It reads the now-updated balance, and if it is no
longer enough, the insert fails with `insufficient_balance` instead of
double-spending.

Retried or duplicate requests are caught separately, by the unique indexes
`idx_transactions_partner_idempotency` and `idx_transactions_qr_code_id`.
